# Работа с кабинетом RU-CENTER (nic.ru) через API

Заметка для будущих сессий: контекст, доступы, план.

## Что уже сделано

- Зарегистрировано OAuth-приложение в кабинете RU-CENTER
  (`https://www.nic.ru/manager/oauth.cgi?step=oauth.app_list` — список приложений).
- Написан клиент `tools/nic.py` — работа с DNS-хостингом через API Руцентра.

## Что нужно для запуска

Сессия обращается к `api.nic.ru`, поэтому окружению нужны сеть и ключи.

### 1. Сетевой доступ

В окружении (claude.ai/code → селектор окружений → иконка настроек) поле
**Network access** переключить на **Custom** и в **Allowed domains** вписать:

```
api.nic.ru
www.nic.ru
```

Отметить **Also include default list of common package managers**, иначе
отвалится всё остальное (npm, PyPI, GitHub-прокси не затрагивается).

### 2. Переменные окружения

В том же диалоге, поле **Environment variables**, формат `.env`:

```
NIC_CLIENT_ID=логин приложения
NIC_CLIENT_SECRET=пароль приложения
NIC_USERNAME=1234567/NIC-D
NIC_PASSWORD=пароль от договора
```

`NIC_USERNAME` — строго в формате `номер_договора/NIC-D`.

Важно: значения окружения видны всем, кто пользуется этим окружением, и
хранятся в его конфигурации. Отдельного хранилища секретов пока нет.

### 3. Новая сессия

Запущенные сессии читают переменные один раз при старте. После правки
настроек нужна новая сессия — текущая изменения не увидит.

## Проверка

```bash
python3 tools/nic.py token      # получить токен
python3 tools/nic.py domains    # домены: NS, DNSSEC, флаги
python3 tools/nic.py services   # все услуги: сроки и автопродление
python3 tools/nic.py expiring   # что истекает в ближайшие 90 дней
python3 tools/nic.py dnscheck   # фактические MX/SPF/DMARC/CAA + проблемы
```

`dnscheck` ходит не в Руцентр, а к публичному резолверу (DoH `dns.google`) —
зоны этого договора API не отдаёт, снаружи они видны, изнутри нет.

Если `token` падает с HTTP 401 — чаще всего дело в формате `NIC_USERNAME`.

## Разделы API и права

Токен выдаётся под конкретные права (`scope`), они заданы в `nic.py`
(`DEFAULT_SCOPE`) и переопределяются переменной `NIC_SCOPE`. Пути в scope —
это регулярки, поэтому раздел перечисляется дважды: `GET:/domains` и
`GET:/domains/.+`, иначе запрос к самому `/domains` не подойдёт под правило.

Кэш токена помнит, под какой scope он выдан: после расширения прав токен
перевыпускается сам.

| Раздел            | Формат | Что отдаёт                              |
|-------------------|--------|-----------------------------------------|
| `/domains`        | JSON   | домены, NS, DNSSEC, флаги               |
| `/services`       | JSON   | все услуги: сроки, автопродление        |
| `/dns-master/...` | XML    | зоны и записи DNS-хостинга              |

Разделов `/contracts`, `/dns`, `/cloud-dns` в API нет — они отдают
HTML-заглушку сайта, а не данные.

## Важно: править DNS через этот клиент нельзя

`dns-master` на договоре пуст: услуги «DNS-хостинг» нет, зон в этом разделе
ноль. При этом домены делегированы на NS Руцентра и записи отдаются —
зоны живут на новой «облачной» платформе (`ns*-cloud.nic.ru`), которую этот
API не показывает.

Практический вывод: `zones`, `records`, `add`, `delete`, `commit` работать не
будут — редактировать записи можно только через веб-кабинет. Читать текущее
состояние DNS удобно через публичный резолвер (DoH `dns.google` доступен).

## Модель работы клиента

Изменения записей копятся в черновике зоны и вступают в силу только
после `commit` (так устроен API Руцентра). `rollback` отменяет черновик.
Это позволяет показать точный диф до применения.
